# 0003. Мониторы API как цели парсинга с `api_key_id`, изоляция от админки фильтрами

- **Статус:** Принято
- **Дата:** 2026-10-13
- **Задача:** #13, PR #17

## Контекст

Публичному API понадобились мониторы цен (`/v1/monitors`). В админке мониторинг уже был: таблица `parse_targets` с расписанием, планировщик `services/monitoring.py`, история в `price_snapshots`, оповещения в `price_alerts`. Мониторы клиентов API не должны попадать в админку и отчёты владельца, а данные одного ключа не должны быть видны другому.

## Решение

- Монитор API хранится строкой `parse_targets` с заполненным `api_key_id`. У целей админки `api_key_id` = NULL.
- Тот же планировщик перепроверяет и те, и другие цели.
- Админка и отчёты фильтруют данные через `admin_owned()` и `not_api_owned()` (`models/parse_target.py`). Каждый запрос к целям, снимкам цен и оповещениям в админке обязан их использовать.
- Мониторы API не пишут в `parsed_products`, их цены берутся из `price_snapshots`.
- Предыдущая цена для монитора API ищется только по его `target_id`, для цели админки по URL (`_previous_price`).

## Альтернативы

- **Отдельные таблицы для мониторов API.** Пришлось бы дублировать планировщик и логику оповещений.
- **Общие данные без разделения.** Клиенты API видели бы цели владельца и друг друга.

## Последствия

- Один планировщик и одна логика оповещений.
- Забытый фильтр в новом запросе админки покажет данные клиентов API. Это проверяют тесты изоляции в `tests/test_api_monitors.py`.
- На ключ можно создать до 500 мониторов, одну ссылку один ключ добавляет только один раз.
