# 0002. API-ключи в базе только в виде SHA-256, ключ из настроек импортируется один раз

- **Статус:** Принято
- **Дата:** 2026-10-13
- **Задача:** #13, PR #17; публичный ключ из примера убран в #19, PR #20

## Контекст

Раньше API проверял один ключ из `data/settings.yml` (`security.api_key`). Его нельзя было отозвать, не сломав всех клиентов, нельзя было выдать разным клиентам разные ключи, а значение из `settings.yml.example` было опубликовано в репозитории.

## Решение

- Ключи хранятся в таблице `api_keys` (`models/api_key.py`). Ключ генерирует сервер (`grx_` + `secrets.token_urlsafe(32)`), показывает один раз, в базе остаётся только SHA-256 и первые символы для показа.
- Быстрый хеш без соли достаточен: ключ состоит из случайных 256 бит, перебор невозможен.
- Ключ из `security.api_key` один раз переносится в базу при старте (`import_legacy_key`), чтобы старые интеграции продолжили работать. Ключ с уже известным хешем повторно не импортируется, поэтому отзыв в панели сохраняется.
- Проверка ключа закрыта по умолчанию: если база недоступна, API отвечает 503 и не откатывается на ключ из настроек.
- В примере настроек поле пустое (#19), а старый публичный ключ `DEFAULT_LEGACY_KEY` помечается в панели как небезопасный.

## Альтернативы

- **Хранить ключи открытым текстом.** Утечка базы раскрыла бы все ключи.
- **bcrypt или argon2.** Медленный хеш нужен для паролей с низкой энтропией, здесь он только замедлял бы каждый запрос.
- **Оставить один ключ в настройках.** Нет отзыва и разделения клиентов.

## Последствия

- Потерянный ключ не восстановить, только выпустить новый.
- Отзыв ключа останавливает его мониторы, удаление стирает всё, что создано через него.
- Кэшировать результат проверки ключа нельзя: отзыв должен действовать сразу.
