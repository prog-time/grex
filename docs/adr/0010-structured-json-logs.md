# 0010. Структурированные логи в `logs/app.jsonl` средствами Loguru

- **Статус:** Предложено
- **Дата:** 2026-11-07
- **Задача:** #76

## Контекст

Логи были только текстом: терминал, страница логов админки и `logs/ГГГГ-ММ-ДД.log`. Найти по ним ошибку программой или собрать все строки одного запроса было нельзя. В строке не было ни ссылки, ни площадки, ни номера задачи (поле контекста всегда равно `SYSTEM`). Логи uvicorn шли мимо Loguru и не попадали ни в файл, ни в админку. Трассировки печатались через `traceback.print_exc()` только в терминал. Логин прокси писался открытым текстом. Прогон тестов писал ошибки-фикстуры в настоящую папку `logs/`.

Логи нужны и человеку, и Claude, который разбирает ошибки по файлам, а позже через хранилище логов (VictoriaLogs или Loki) и MCP. Для этого нужен один машиночитаемый формат с контекстом и без секретов.

## Решение

- `setup_logger()` пишет дополнительный файл `logs/app.jsonl`: одна строка JSON на запись. Обязательные поля: `ts` (UTC), `level` (`debug`/`info`/`warning`/`error`/`critical`), `service`, `version`, `env`, `msg`, `logger`, `function`, `line`. Для ошибок добавляется `error.{type,message,stack}`. Контекст из `logger.contextualize(...)` идёт полями верхнего уровня. Ротация в полночь, хранение 14 дней. Текстовые форматы не меняются.
- JSON собирается своей функцией формата, а не `serialize=True`: встроенная сериализация Loguru даёт свою вложенную схему (`text` + `record`), неудобную для поиска.
- Контекст ставится в точках входа: `request_id` в HTTP middleware (и заголовок `X-Request-ID` в ответе), `url` и `marketplace` в `ParsingService.parse_product`, `target_id`, `job_id`, `session_id` в фоновых задачах.
- Одна функция-патчер обрабатывает каждую запись до всех мест назначения: подставляет метку контекста, скрывает секреты (`redact()`) в сообщении, значениях контекста и тексте исключения и заранее готовит трассировку. Поэтому терминал, админка и оба файла показывают одинаковый, уже очищенный текст.
- Каждая строка знает, чьё это действие: поле `actor` (`admin:<имя>`, `api_key_id:<id>`, `anonymous`, `system`). Его ставят зависимости авторизации через переменную контекста, поэтому оно есть и у строк внутри обработчика, и у фоновых задач, запущенных из запроса.
- Каждое изменение и каждый вызов публичного API — строка `event="http.request"` уровня `INFO` с методом, путём, статусом и временем. Просмотры страниц, опрос и статика остаются на `DEBUG`, иначе `INFO` утонет в шуме. Тела запросов не пишутся: в них бывают пароли и токены, а объект действия и так виден в пути и в строке обработчика. Отдельные именованные события: вход, выход и неудачный вход в админку, итог парсинга.
- Стандартный `logging` перехватывается (`InterceptHandler`), `uvicorn.run` получает `log_config=None`.
- Браузерный подпроцесс (ADR 0009) при `spawn` настраивает логгер сам (`setup_logger(child=True)`: без SSE, без ротации, без очереди) и получает контекст вызывающего кода. При `fork` обработчики наследуются, и строки уходят через очередь `enqueue` в процесс-родитель.
- Каталог логов можно переопределить переменной `GREX_LOG_DIR`. Тесты задают в ней временную папку.
- Новых зависимостей нет.

## Альтернативы

- **`structlog` или `python-json-logger`.** Это новая зависимость и второй способ логирования рядом с Loguru. Loguru умеет всё нужное сам.
- **`serialize=True` в Loguru.** Без своей функции формата JSON получается вложенным и неудобным для поиска.
- **Перевести текстовый файл на JSON вместо добавления второго файла.** Людям, которые читают `logs/*.log` глазами, стало бы хуже. Два файла стоят немного места на диске.
- **Отправлять логи по сети прямо из приложения.** Это связало бы приложение с инфраструктурой логов. Файл переживает падение хранилища, а сборщик (Vector, Alloy) читает его отдельно.

## Последствия

- По `app.jsonl` ошибки ищутся через `jq` (примеры в `RUNBOOK.md`), позже тот же файл читает сборщик для хранилища логов.
- Каждая новая фоновая точка входа должна ставить свой идентификатор через `logger.contextualize(...)`.
- `setup_logger()` вызывается один раз на процесс, а не один раз вообще.
- Набор шаблонов в `redact()` нужно дополнять, когда появляется новый вид секрета, и покрывать тестом. Фильтр — это страховка, он не разрешает передавать секреты в лог.
- Передача контекста в подпроцесс читает приватную переменную Loguru (`loguru._logger.context`). Если в новой версии Loguru она изменится, подпроцесс будет писать без контекста, но не упадёт.
- Сама трассировка теперь форматируется модулем `traceback`, без значений локальных переменных (`diagnose` Loguru), поэтому секреты из переменных не попадают в лог.
