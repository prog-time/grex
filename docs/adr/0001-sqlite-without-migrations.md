# 0001. SQLite и добавление колонок через `_ADDED_COLUMNS` вместо миграций

- **Статус:** Принято (решение было принято раньше, записано задним числом)
- **Дата:** 2026-10-14
- **Задача:** #54

## Контекст

Проект ставят себе люди без опыта администрирования: `./start.sh` должен поднять всё сам, без отдельного сервера базы данных. Данных немного: цели парсинга, последние карточки товаров, история цен, журнал запусков. Схема растёт постепенно: колонки мониторинга в `parse_targets`, `api_key_id`, `chat_id` в `alert_sources`.

## Решение

- База: SQLite в файле `data/admin.db`, доступ через SQLAlchemy (async, `aiosqlite`).
- Таблицы создаёт `Base.metadata.create_all()` при старте (`init_db()` в `models/job.py`).
- Новая колонка в существующей таблице добавляется в `_ADDED_COLUMNS` в `models/job.py`, при старте `_migrate_added_columns()` выполняет `ALTER TABLE … ADD COLUMN` для отсутствующих колонок. Комментарий в коде называет это «lightweight, dependency-free column migration».

## Альтернативы

- **PostgreSQL или MySQL.** Отдельный сервер усложняет установку для целевых пользователей.
- **Alembic.** Полноценные миграции, но ещё одна зависимость и шаг при обновлении. Для одних только добавлений колонок не нужен.

## Последствия

- Установка без внешней базы, для бэкапа достаточно скопировать один файл.
- Можно только добавлять колонки. Переименование, удаление, смена типа и новые ограничения требуют нового ADR и ручного переноса данных (или перехода на Alembic).
- Внешний ключ в базе один (`api_job_items.job_id`), остальные связи логические и держатся кодом, см. `docs/architecture/erd.md`.
- SQLite плохо переносит параллельную запись из нескольких процессов, поэтому сервер работает одним процессом (см. ADR 0006).
