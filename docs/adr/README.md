# Архитектурные решения (ADR)

Здесь записаны решения, которые заметно влияют на устройство проекта: почему выбран именно такой подход, что рассматривали вместо него и к чему это обязывает. Код показывает, *что* сделано, ADR объясняет *почему*.

## Когда писать ADR

- меняется стек: новая зависимость, фреймворк, хранилище;
- меняется граница компонентов или способ их взаимодействия;
- меняется модель данных так, что это нельзя сделать через `_ADDED_COLUMNS` (переименование, удаление колонки);
- выбранное решение неочевидно и через полгода его захотят «исправить».

Мелкие решения внутри одного модуля ADR не требуют.

## Как писать

1. Скопируйте [`0000-template.md`](0000-template.md) в `NNNN-короткое-название.md` со следующим свободным номером.
2. Заполните разделы и поставьте статус «Предложено».
3. Сошлитесь на ADR в задаче и PR. После слияния PR смените статус на «Принято».
4. Принятый ADR не переписывают. Если решение меняется, пишут новый ADR, а у старого ставят статус «Заменено ADR NNNN».
