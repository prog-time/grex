# Как вносить изменения

Правила одни и для людей, и для Claude Code. Они нужны, чтобы по истории было видно, какая задача привела к какому изменению и почему.

## Порядок работы

1. **Задача.** Каждое заметное изменение начинается с Issue на GitHub. Шаблоны: баг, новая возможность, улучшение, документация, вопрос. В задаче описано, что делаем, зачем, и критерии «готово когда». Большую задачу делите на несколько маленьких.
2. **Ветка** от свежего `main` с номером задачи: `issues-N`, например `issues-123`. В ветке без номера не коммитят, в `main` напрямую тоже.
3. **Коммиты** с префиксом задачи: `issues-123|add seller links via internal API`. Сообщение короткое, в повелительном наклонении, по-английски. В одном коммите одно связанное изменение.
4. **Pull Request** в `main`. В заголовке название задачи, в описании `Closes #N` и разделы из шаблона PR: что изменилось, как теперь работает, почему так, как проверено (и что не проверялось), что осталось.
5. **Слияние** после зелёного CI и ревью.

С Claude Code те же шаги делают команды `/task_create`, `/task_branch`, `/task_complete`, `/task_submit`.

## Проверки

Подключите git-хуки один раз после клонирования:

```bash
make hooks
```

| Когда | Что проверяется |
|---|---|
| `git commit` | `ruff` по изменённым `.py`; `mypy`, если файл в проверяемом пакете; предупреждение, если у сервиса нет теста. Хук добавляет `issues-N|` к сообщению |
| `git push` | `ruff check .` и все тесты `pytest` |
| CI на каждый PR | Lint (ruff), Type check (mypy), Tests (pytest), Smoke (запуск приложения и обход всех разделов панели) |

Хуки и CI проверяют одно и то же, только CI полнее. `--no-verify` не используйте: если проверка мешает, чините проверку отдельной задачей.

Вручную:

```bash
.venv/bin/ruff check .
.venv/bin/mypy
.venv/bin/python -m pytest
```

## Документация в том же PR

Задача не готова, пока не обновлено то, что она изменила. Чек-лист есть в шаблоне PR и в [`rules/process/ai-workflow.md`](rules/process/ai-workflow.md):

- схемы в [`docs/architecture/`](docs/architecture/), если меняются компоненты, таблицы, сценарии или состояния;
- [ADR](docs/adr/), если принято решение, влияющее на устройство проекта или стек;
- `CHANGELOG.md`, раздел `Unreleased`, если изменение заметно пользователю или клиенту API;
- `README.md`, если меняется установка или использование;
- [`RUNBOOK.md`](RUNBOOK.md) или `rules/domain/`, если выяснилось что-то неочевидное о площадке или работе сервиса.

## Зависимости

Новую библиотеку, фреймворк или замену существующей сначала обсуждают в задаче: зачем, какие есть альтернативы, во что обойдётся. Решение записывают в ADR. Затем меняют `requirements*.txt` и выполняют `make lock`, чтобы обновить `requirements-ci.txt`. Обновления версий предлагает Dependabot, их принимают только с зелёным CI.

## Релиз

1. PR, который поднимает версию в файле `VERSION` и переносит записи из `Unreleased` в раздел новой версии `CHANGELOG.md`.
2. После слияния: тег `vX.Y.Z` и GitHub Release из `main`.

Если `VERSION` меньше последнего тега, тесты падают (ADR 0007).

## История

Коммиты в `main` до появления хуков (около 60) не содержат номера задачи. Переписывать их не нужно: правило действует для всех новых изменений.
